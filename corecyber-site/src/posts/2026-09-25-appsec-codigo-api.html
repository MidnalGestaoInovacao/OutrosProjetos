Um desenvolvedor sobe uma correção às pressas numa sexta à noite. Junto vai um arquivo de configuração com a senha do banco de dados. Ninguém percebe — até que alguém de fora perceba. Muitas das falhas que chegam à produção nasceram meses antes: numa linha de código, numa biblioteca desatualizada ou numa API publicada sem revisão.

Uma sopa de siglas, explicada

Segurança de aplicações, o tal AppSec, tem fama de difícil, em parte por causa das siglas. Mas elas descrevem ideias simples:

  • SAST (teste estático): lê o código-fonte em busca de padrões inseguros, como uma consulta ao banco montada com o texto que o usuário digitou. É revisar a receita antes de cozinhar.
  • SCA (análise de composição): confere as bibliotecas de terceiros que o seu software usa e aponta as que têm falhas conhecidas. Muito do que roda no seu sistema não foi escrito pela sua equipe — e também precisa ser vigiado.
  • Segredos expostos: senhas, chaves de API e tokens esquecidos no repositório.
  • DAST (teste dinâmico): testa a aplicação em execução, de fora para dentro, como faria um atacante. É provar o prato pronto.
  • SBOM (lista de materiais de software): o inventário de todos os componentes do seu software, com versões. A lista de ingredientes.
  • SARIF: um formato padrão para resultados de análise, que outras ferramentas de desenvolvimento conseguem ler.

O que o CoreCyber analisa

No código, a análise junta SAST, dependências (SCA) e segredos expostos, e gera o SBOM no padrão CycloneDX 1.5.

Na aplicação, a segurança de APIs é testada de forma dinâmica (DAST) a partir da especificação OpenAPI — o documento que descreve cada rota, parâmetro e resposta da sua API. Com o teste autenticado (white box, ou caixa branca), o teste usa o acesso que você fornece e vai além da tela de login, onde costumam estar os dados que importam.

E há o ponto que costuma faltar: a correlação entre o código e a aplicação em execução. Quando um achado do código também aparece na aplicação rodando, a conversa sobre “isso é falso positivo?” fica bem mais curta — e a prioridade, mais evidente.

Você sabia?

Na edição de 2023 do OWASP API Security Top 10, o primeiro lugar ficou com a falha de autorização em nível de objeto (BOLA, na sigla em inglês): a API não confere se quem pede um registro tem direito àquele registro específico. Às vezes, basta trocar um número no endereço da requisição para ver o pedido de outro cliente. É o tipo de falha que costuma exigir teste autenticado para aparecer.

SBOM: a lista de ingredientes que vão pedir a você

Quando uma falha grave aparece numa biblioteca popular, a primeira pergunta é: “nós usamos isso?”. Sem um SBOM, a resposta exige vasculhar repositórios. Com ele, é uma busca.

O CycloneDX, formato usado pelo CoreCyber, é mantido pela OWASP em conjunto com a Ecma International e foi padronizado internacionalmente como ECMA-424. Um SBOM nesse formato pode ser lido por outras ferramentas, entregue a clientes que pedem transparência sobre o software e guardado como evidência.

Resultados que entram no fluxo de quem desenvolve

Relatório de segurança que ninguém abre não corrige nada. Por isso, os resultados saem em cinco formatos: PDF para a gestão, Excel e CSV para quem prefere planilha, JSON para integrações e SARIF, o padrão aberto da OASIS para resultados de análise, que ferramentas de desenvolvimento conseguem importar.

E, como tudo está na mesma plataforma, a falha da API não vive numa ferramenta separada da falha do servidor: a equipe olha um painel só, com superfície de ataque, vulnerabilidades e disponibilidade.

Como começar

  1. Escolha um repositório que vai para produção em breve — ou aquele mais antigo, em que ninguém quer mexer.
  2. Comece pelos segredos expostos. São rápidos de corrigir e perigosos de ignorar. Lembre-se: apagar a senha do código não basta, porque ela continua no histórico. Troque a senha.
  3. Gere o SBOM e guarde-o como evidência da versão.
  4. Teste a API a partir da especificação OpenAPI, com credenciais de teste para o teste autenticado.
  5. Exporte para cada público: SARIF para o time de desenvolvimento, PDF para a gestão.

Para entender cada categoria de falha, o OWASP Top 10, cuja edição mais recente é a de 2025, continua sendo o melhor ponto de partida.
